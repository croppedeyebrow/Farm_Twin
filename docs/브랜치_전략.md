# 브랜치 전략

30일 MVP·소규모 팀 기준으로 **trunk-based**에 가깝게 운영한다.

## 브랜치

| 브랜치 | 역할 |
|---|---|
| `main` | 배포·데모 가능 상태. 직접 push보다 PR 병합을 기본으로 한다. |
| `feature/<주제>` | 기능·문서·인프라 작업 브랜치 |
| `fix/<이슈>` | 버그 수정 |
| `chore/<주제>` | 설정·의존성·CI 등 유지보수 |

기본 작업 흐름은 `feature/*` → PR → `main`이다.

## 규칙

1. `main`은 항상 기동·테스트 가능한 상태를 목표로 한다.
2. 한 PR은 한 단계 또는 한 관심사로 범위를 제한한다.
3. 단계 완료 기준을 통과하기 전 다음 단계 작업을 `main`에 넣지 않는다.
4. 장기 생존 `develop` 브랜치는 두지 않는다. (동기화 비용 대비 이득이 작음)
5. 릴리스 태그는 공개 데모 시점에 `v0.1.0` 형식으로 단다.

## 네이밍 예시

- `feature/day1-baseline`
- `feature/domain-db`
- `fix/health-ready`
- `chore/pin-node-22`
