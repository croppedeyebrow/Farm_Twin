# 백엔드 설계

## 1. 서비스 책임

### API 서비스

- 농장·재배실·센서·액추에이터·규칙 CRUD
- 이력과 최신 snapshot 조회
- 시뮬레이션 실행 제어
- WebSocket 인증·연결·push
- 수동 제어 명령 수신

### Simulator Worker

- simulation clock
- 환경 상태전이 계산
- 가상 센서 측정
- 규칙 판정
- 가상 액추에이터 적용
- readings, commands, events 저장

API와 simulator는 최종 배포에서 별도 프로세스·컨테이너로 실행한다.

## 2. 계층

```text
routers → application services → domain → repositories → PostgreSQL
                         └→ event publisher
```

- router에 규칙·DB 쿼리를 넣지 않는다.
- 도메인 계산은 FastAPI 요청 객체에 의존하지 않는다.
- 시뮬레이터는 REST를 거치지 않고 application/repository 계약을 사용한다.

- SimulatedSensorSource

## 5. 실행 모드

| 모드 | 목적 |
|---|---|
| DEMO | 1개 재배실의 물리적 인과관계 시연 |
| REPLAY | 동일 입력과 seed로 회귀 테스트 |
| FAULT | 센서 고장과 복구 검증 |
| LOAD | 다수 농장·센서·클라이언트 성능 검증 |

## 6. 폐쇄 루프 순서

1. 외기·현재 FarmState 로드
2. 이전 액추에이터 상태 반영
3. 다음 FarmState 계산
4. 가상 센서 측정 생성
5. 품질 정책 적용
6. 규칙 판정
7. ControlCommand 생성
8. 가상 액추에이터 적용
9. ControlEvent 기록
10. DB commit 후 실시간 이벤트 발행

## 7. 중복과 경쟁조건 방어

- simulation_run에는 한 명의 active worker만 허용
- worker lease 또는 PostgreSQL advisory lock 사용
- command에 idempotency key 적용
- 상태 갱신에 version 또는 `SELECT FOR UPDATE` 적용
- DB commit 전 WebSocket 발행 금지
