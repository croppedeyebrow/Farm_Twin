# 6단계 — 데이터 파이프라인과 고장 주입

## 기간

Day 20~23

## 목표

센서 데이터의 계약·품질·lineage를 확립하고 고장 상황을 재현한다.

### Day 22

- [x] spike, stuck, dropout 주입
- [x] 고장 시작·해제 이력
- [x] 규칙 엔진의 bad 측정 정책

> 고장은 측정 경로에만 적용되고 참값(FarmState)은 그대로다. 샘플에 고장 표시가 없으므로
> 품질 검사가 직접 잡아야 한다 — spike 는 변화율(suspect), stuck 은 flatline 4회 연속(bad,
> PPFD 제외), dropout 은 stale → 복구 시 sequence gap(missing). 룸 규칙은 step 마다 측정값+품질로
> 평가되며 suspect 는 보류, bad/missing/stale 은 차단하고 차단 시작 시점만 REJECTED 이벤트로 남긴다.

### Day 23

- [x] replay dataset export/import
- [x] run/model/rule lineage
- [x] 1분 집계와 이력 조회
- [x] 데이터 품질 리포트

> run 은 첫 step 직전 상태를 체크포인트(`initial_state`)로 남긴다: 참값, 설비 출력, 센서별 수신
> 판정 상태, 송신 커서, 규칙 게이트, 진행 중인 품질 차단. step 마다 외기 스냅샷도 저장한다.
> `farmtwin.replay.v1` 데이터셋에는 체크포인트, 외기, 스텝 간격, 고장(해제 시각 포함), 수동 제어,
> 기대 readings·commands가 들어간다. import 하면 같은 룸의 재생 run 이 만들어지고, 실행 후
> `(센서, source_sequence)` 단위로 원본과 비교한다. 고장은 활성 플래그가 아니라 시작·해제 시각으로
> 적용하므로 과거 구간도 같은 시각에 다시 재현된다. 수동 제어도 명령·이벤트로 기록된다.
> 규칙 명령에는 규칙 개정 번호와 판정 근거 reading 이, run 에는 활성 규칙 묶음 지문
> (`rules.v1:<sha12>`)이 남는다.
>
> - 이벤트 lineage 추적: `GET /control-events/{id}/lineage`
>   (이벤트 → 명령 → 규칙 개정 → 근거 측정 → 외기 스냅샷 → run)
> - 이력 조회: `GET /farms/{id}/readings/history?bucket_seconds=0|60|300`
>   (가상 시계 기준, 평균·범위는 good 행만 사용)
> - 품질 리포트: `GET /farms/{id}/quality-report`
